This chapter describes the framework in which provider-selective distillation is
studied. Section~\ref{imp:sec:overview} gives an overview of the training loop.
Section~\ref{imp:sec:tasks} describes the three task domains and how answers are
checked, and Section~\ref{imp:sec:providers} the student and the providers.
Section~\ref{imp:sec:update} specifies the training objective and
Section~\ref{imp:sec:selectors} the curriculum selector and the curricula it is
compared with. Section~\ref{imp:sec:protocol} gives the evaluation protocol and
configuration, Section~\ref{imp:sec:verification} reports how the testbed was verified,
and Section~\ref{imp:sec:limitations} lists the limitations of the design. The tasks,
checkers, student and training loop were built and used for the preliminary study of
Chapter~\ref{chap:Evaluation}. The training objective with token probabilities is
specified here but has not yet been run; Section~\ref{imp:sec:status} states exactly
what is implemented.

The notation follows Section~\ref{sec:Problem Statement}. The student is $\pi_\theta$,
the providers are $M_1, \dots, M_K$, prompts come from domains
$\mathcal{X}_1, \dots, \mathcal{X}_D$, an arm is a pair $a = (k, d)$, and each round
uses a batch of $b$ prompts.

\section{Overview}
\label{imp:sec:overview}

A training run alternates between choosing an arm and learning from it
(Figure~\ref{imp:fig:loop}). The selector observes the student's accuracy in each
domain and picks an arm $(k, d)$. The student answers $b$ prompts from domain $d$,
sampling $G$ responses to each. Every response is checked for correctness, and
provider $k$ scores the student's responses token by token. The student then takes one
gradient step. After every block of $L$ rounds the student is evaluated on a held-out
selection set, and the result is passed back to the selector.
Algorithm~\ref{imp:alg:run} gives the complete procedure.

\begin{algorithm}[htbp]
\caption{One training run}
\label{imp:alg:run}
\begin{algorithmic}[1]
\Require student $\pi_\theta$ with a fresh LoRA adapter, providers $M_1, \dots, M_K$,
  number of rounds $T$, block length $L$
\State $t \gets 0$
\State $\alpha \gets$ \Call{Evaluate}{$\pi_\theta$} \Comment{per-domain selection accuracy}
\While{$t < T$}
  \State $(k, d) \gets$ \Call{Select}{$\alpha$}
  \State $\alpha_{\mathrm{before}} \gets \alpha$
  \For{$L$ rounds, while $t < T$}
    \State draw the next $b$ prompts $x_1, \dots, x_b$ from $\mathcal{X}_d$
    \State sample $y_{i,1}, \dots, y_{i,G} \sim \pi_\theta(\cdot \mid x_i)$ for each $i$
    \State reward each response (Section~\ref{imp:sec:update})
    \State read $M_k$'s token probabilities on the responses
    \State take one gradient step (Eq.~\ref{imp:eq:total}); $t \gets t + 1$
  \EndFor
  \State $\alpha \gets$ \Call{Evaluate}{$\pi_\theta$}
  \State \Call{UpdateSelector}{$(k, d)$, $\alpha_{\mathrm{before}}$, $\alpha$}
\EndWhile
\State evaluate on the full selection and test sets
\end{algorithmic}
\end{algorithm}

\section{Tasks and Answer Checking}
\label{imp:sec:tasks}

\subsection{Domains}
\label{imp:sec:domains}

Three single-turn domains are used, each with answers that can be checked by a
program. Table~\ref{imp:tab:domains} summarises them. Every domain is split into a
prompt pool of 2,000 items, on which the student trains, a selection set of 500 items, which supplies the selector's
feedback, and a test set of 500 items, which is used only for final results. The three
splits are disjoint within each domain.

\paragraph{Countdown.} Given three integers and a target, the model must write an
arithmetic expression that uses each integer exactly once and evaluates to the target,
inside \texttt{<answer>} tags. Countdown is retained from the motivating experiment of
Section~\ref{pre:sec:motivating}, so that its answer checker is shared. Puzzles come
from the dataset released with GOLD \autocite{patino_gold_2025}.\footnote{\url{https://huggingface.co/datasets/HuggingFaceTB/Countdown-Task-GOLD}}
The pool is drawn from its 80,000-puzzle training configuration and the selection and
test sets from its 10,000-puzzle test configuration. Four-number puzzles were excluded
after screening: the base student solved 0.8\% of them, and only 6\% of its groups of
eight responses contained both a correct and an incorrect answer, so reinforcement
learning would have had almost nothing to learn from. On three-number puzzles the
corresponding figures were 6\% and 32\%.

\paragraph{MATH.} Competition mathematics problems at difficulty levels 3 to 5
\autocite{hendrycks_math_2021}, of which there are 5,586 in the training split and 3,669
in the test split. The pool and selection set come from the training split and the
test set from the test split. Prompts ask for step-by-step reasoning and a final answer
in \verb|\boxed{}|.

\paragraph{Code.} Python function-writing problems from KodCode-V1
\autocite{xu_kodcode_2025}, each with a pytest test file. Of its 484,097 problems, 65,087
remain after keeping instruction-style problems with a single target function, medium
or hard difficulty, no pytest fixtures or parametrisation, and a reported similarity
below 0.8 to existing benchmarks. Each problem's reference solution was then run against
its tests in the sandbox described below, and only problems whose reference passes were
kept (3,608 of 3,900 sampled candidates, 92.5\%). The prompt states the required
function signature.

\paragraph{Domains considered and rejected.} GSM8K \autocite{cobbe_gsm8k_2021} was the
original mathematics domain, but Qwen2.5-7B, Qwen2.5-14B, Qwen2.5-32B and Phi-4 all
answered between 94 and 97\% of screening prompts correctly, which leaves almost no
difference between providers for a selector to exploit. MBPP \autocite{austin_mbpp_2021} was the original
code domain, but it contains only 974 problems in total, too few for a 2,000-prompt pool.

\subsection{Canonical answers and agreement}
\label{imp:sec:canonical}

Scoring a response needs its final answer, not its wording. The
testbed reduces every response $y$ to a canonical final answer
$\kappa_d(y)$, or to $\varnothing$ when no valid answer can be extracted, and two
responses agree when their canonical answers are equal. The canonical form is chosen so
that different but equivalent answers compare equal.

\begin{description}[itemsep=3pt,topsep=4pt]
  \item[Countdown.] The expression in the last \texttt{<answer>} tag, with any trailing
    ``$= v$'' removed and LaTeX operators and delimiters normalised. If it uses exactly
    the given integers, $\kappa$ is its value rounded to four decimal places; otherwise
    $\kappa = \varnothing$. Two different expressions with the same value therefore
    agree.
  \item[MATH.] The content of the last \verb|\boxed{}|, parsed and normalised by the
    Math-Verify library,\footnote{\url{https://github.com/huggingface/Math-Verify}} so
    that, for example, $0.5$ and $\frac{1}{2}$ have the same canonical form.
  \item[Code.] The function's behaviour on the test inputs. The longest Python code block
    is extracted and run in the sandbox, and $\kappa$ is the tuple of values the target
    function returns, or the exception it raises, on the inputs used by the tests. The
    expected outputs are not used, so two programs agree when they behave identically,
    whether or not either is correct.
\end{description}

Canonical answers are used to detect prompts on which all of the student's responses
give the same answer (Section~\ref{imp:sec:update}) and for the agreement reward of the
preliminary study (Section~\ref{pre:sec:setup}). Correctness is checked separately: a Countdown answer must equal the target, a MATH answer must be
judged equivalent to the reference by Math-Verify, and a program must pass every test.

\subsection{Sandbox and harness rules}
\label{imp:sec:sandbox}

Generated programs run in a bubblewrap sandbox\footnote{\url{https://github.com/containers/bubblewrap}}
with a read-only file system, no network access, a 4\,GB memory limit and time limits
of 5 seconds to load a program and 2 to 3 seconds per test. Before running, the code is
reduced to its module-level imports, definitions and assignments, which removes the
self-tests, print statements and input-reading code that models often append, and
\texttt{from typing import *} is prepended so that type hints such as
\texttt{List[int]} do not fail for lack of an import. These rules were added after
screening showed well-formed functions being scored as missing answers, and they apply
identically to the student and to every provider.

\section{Student and Providers}
\label{imp:sec:providers}

\paragraph{Student.} The student is Qwen2.5-1.5B-Instruct \autocite{qwen_qwen25_2024},
trained through a LoRA adapter \autocite{hu_lora_2022} of rank 16 on every linear layer
of the attention and feed-forward blocks. A rank of 64 was measured to add only 1.5\%
to the time per step, so cost does not constrain the choice of rank. A student of this
size is chosen because the learnability gap reported for models of 3B parameters or
fewer \autocite{li_learnability_gap_2025} is the regime in which the strongest provider
is least likely to be the most useful one. Before training the student scores 0.208 on
Countdown, 0.474 on MATH and 0.396 on code on the selection set.

\paragraph{Providers.} The providers are three open-weight models of the student's
family, which therefore share its tokenizer (Table~\ref{imp:tab:pool}): a small general
model the student can plausibly catch up with, a larger general model, and a code
specialist of the same size. The pool is a subset of the five providers of the
preliminary study. The two Phi models of that study use a different tokenizer and are
left out, because token-level supervision across tokenizers recovered far less in our
motivating experiment (Section~\ref{pre:sec:motivating}).

\section{Training Objective}
\label{imp:sec:update}

This section instantiates the operator $\operatorname{Update}$ of
Section~\ref{sec:Problem Statement}. The objective has two terms. A reward on the
student's own responses, optimised by policy gradient, ties the student to the correct
answer. A divergence to the selected provider's token probabilities supplies supervision
at every position of every response.

\paragraph{Reward term.} Each round produces $G$ responses for each of the $b$ prompts.
Response $y_{i,g}$ receives the reward $r_{i,g} = 1$ if its answer is correct and 0
otherwise. Rewards are turned into group-relative advantages as in GRPO
(Chapter~\ref{chap:Preliminaries}),
\[
  A_{i,g} = \frac{r_{i,g} - \operatorname{mean}_{h}\, r_{i,h}}{\operatorname{std}_{h}\, r_{i,h} + \epsilon},
\]
with $A_{i,g} = 0$ for every response in a group whose rewards are all equal, and the
policy-gradient loss is
\begin{equation}
  \mathcal{L}_{\mathrm{PG}}(\theta) = -\frac{1}{N}
    \sum_{i=1}^{b} \sum_{g=1}^{G} A_{i,g} \sum_{j=1}^{|y_{i,g}|}
    \log \pi_\theta\big(y_{i,g,j} \mid x_i, y_{i,g,<j}\big),
    \qquad N = \sum_{i,g} |y_{i,g}|,
  \label{imp:eq:loss}
\end{equation}
normalised by the total number of response tokens in the batch, as in DAPO
\autocite{yu_dapo_2025}. Because each batch of responses is used for exactly one step,
the importance ratio of GRPO equals one and its clipping never applies.

\paragraph{Provider term.} With provider $k$ selected, the second term is the reverse
KL divergence from the student to the provider at every position of the student's own
responses, as in on-policy distillation \autocite{agarwal_gkd_2024,gu_minillm_2024},
\begin{equation}
  \mathcal{L}_{\mathrm{KD}}(\theta; k) = \frac{1}{N}
    \sum_{i=1}^{b} \sum_{g=1}^{G} \sum_{j=1}^{|y_{i,g}|}
    D_{\mathrm{KL}}\Big( \pi_\theta\big(\cdot \mid x_i, y_{i,g,<j}\big) \,\Big\|\,
                         p_k\big(\cdot \mid x_i, y_{i,g,<j}\big) \Big),
  \label{imp:eq:kd}
\end{equation}
and the student takes one gradient step on
\begin{equation}
  \mathcal{L}(\theta) = \mathcal{L}_{\mathrm{PG}}(\theta)
    + \lambda\, \mathcal{L}_{\mathrm{KD}}(\theta; k),
  \label{imp:eq:total}
\end{equation}
with a weight $\lambda \ge 0$ \TBD[value and schedule of $\lambda$].

\paragraph{Why two terms.} The two terms cover each other's weaknesses. The reward is
exact but sparse: it is one number per response, and a prompt on which all $G$
responses are right, or all wrong, gives no gradient at all. For a binary reward with
success probability $p$ per response, a group is informative with probability
$1 - p^G - (1 - p)^G$, which is 0.22 for $p = 0.03$ and $G = 8$. The preliminary study,
whose update had only a term of this kind, learned on one domain and was unstable
(Section~\ref{pre:sec:countdown}). The provider term is dense, since it supervises
every token of every response whether or not the group is informative, but on its own
it pulls the student towards the provider and no further. With both, the provider
shapes how the student reasons while the reward decides what counts as right, so the
student is not bound by the provider's mistakes. This is the mechanism by which the
framework is intended to let a student pass its teachers (H4).

\paragraph{Cost.} A white-box provider must score the student's fresh responses in
every round, so its outputs cannot be cached in advance. Scoring is one forward pass of
the provider over the batch, without generation, and a 7B provider fits beside the
student on one 48\,GB GPU. Only the selected provider is consulted in a round.

\subsection{Status of the implementation}
\label{imp:sec:status}

The training loop, the reward term with a ground-truth reward, the selector and the
evaluation are implemented and were used in the preliminary study, in which the reward
term was the only term and its reward was either agreement with a provider's answers or,
in a control without any provider, correctness. The provider term of
Equation~\ref{imp:eq:kd} is not yet implemented. The pilot of Chapter~\ref{chap:Plan}
therefore still uses the agreement reward of the preliminary study, and isolates the
other changes of the refined problem: no budget, a larger batch and the simpler
selector.

\section{Curriculum Selector and Reference Curricula}
\label{imp:sec:selectors}

\subsection{Blocks and feedback}

The selector chooses an arm once per block of $L$ rounds. At the end of each block the
student is evaluated greedily, at temperature zero, on the selection set, which gives
its current accuracy $\alpha_d$ in each domain. A block must be long enough for its gain
to stand out from the noise of this evaluation. In the preliminary study a block was 10
rounds of 8 prompts, and over the main runs the gain of such a block on Countdown had a
mean of $+0.023$ and a standard deviation of 0.047, while on MATH and code the mean gain
was below 0.001 with standard deviations of 0.017 and 0.013. Most single observations
were therefore noise. The refined problem uses rounds of $b = 100$ prompts and blocks of
$L = 5$ rounds, so that each decision rests on 500 prompts, and evaluates on all 500
selection prompts per domain.

\subsection{Selector: learned gain per round}
\label{imp:sec:efficiency}

The selector scores each arm by the accuracy gain per round it has actually produced.
After a block of $n$ rounds on arm $(k, d)$ it records the observation
\[
  o = \frac{\alpha_d^{\mathrm{after}} - \alpha_d^{\mathrm{before}}}{n},
\]
the gain on the arm's own domain. Observations are pooled per domain and each arm's
estimate is shrunk towards its domain's:
\[
  \hat{g}_d = \frac{n_0\, g_0 + \sum_{\text{blocks on } d} o}{n_0 + N_d},
  \qquad
  \hat{g}_{k,d} = \frac{m_0\, \hat{g}_d + \sum_{\text{blocks on } (k,d)} o}{m_0 + N_{k,d}},
\]
where $N_d$ and $N_{k,d}$ count the blocks observed. All sums and counts are multiplied
by a discount $\gamma = 0.9$ after every block, because the value of an arm changes as
the student learns. The selector plays the arm with the largest $\hat{g}_{k,d}$, and
with probability 0.1 a random arm, so every arm keeps being observed. The prior $g_0$ is
optimistic, so that untried domains are tried before the selector settles.

Pooling by domain reflects the preliminary study, in which learnability was mostly a
property of the domain: when no provider produces progress on a domain, the selector
learns that for all providers at once. The rule is a simplification of the selector of
the preliminary study, which multiplied a learned efficiency by the headroom between the
provider's accuracy and the student's and divided by the provider's price
(Section~\ref{pre:sec:selectors}). The headroom factor is dropped because headroom
predicted progress poorly: MATH had large headroom and no progress, and on Countdown the
student passed two providers' accuracy. The realised gain already contains whatever
headroom contributes. The price is dropped because there is no budget.

\subsection{Reference curricula}
\label{imp:sec:baselines}

\begin{description}[itemsep=3pt,topsep=4pt]
  \item[Uniform.] A rotation over all arms in a seeded order, so that every arm receives
    the same number of blocks.
  \item[Single provider.] One provider throughout, with domains in rotation. The best of
    these is the reference for H3 and H4.
  \item[Weak to strong.] A fixed order of providers from the smallest to the largest, the
    curriculum suggested by teacher-assistant distillation \autocite{mirzadeh_ta_2020}.
  \item[Bandit curricula from the literature.] Selectors rewarded by the slope of the
    learning curve \autocite{matiisen_tscl_2017} and by the size of the advantages
    \autocite{chen_sec_2025}, applied to arms.
  \item[No provider.] The reward term alone, with domains in rotation, which shows what
    the providers add beyond the labels.
  \item[Supervised fine-tuning.] Training on the providers' own responses, which shows
    what learning on-policy adds.
\end{description}

Uniform, single-provider, no-provider and supervised fine-tuning runs exist for the
preliminary study. The weak-to-strong order and the bandit curricula from the literature
are not yet implemented.

\section{Evaluation Protocol and Configuration}
\label{imp:sec:protocol}
\label{imp:sec:config}

\paragraph{Metric.} The primary result is the learning curve: utility, the mean of the
three domains' accuracies, against the number of prompts the student has trained on.
Curves are drawn from the selection-set evaluations at every block, and final students
are evaluated on all 1,500 test problems. Curricula are compared at equal numbers of
training prompts.

\paragraph{Seeds and uncertainty.} Every condition is run with three seeds. Intervals
are 95\% bootstrap intervals over seeds and test items, and curricula are compared by
paired differences on the same seeds and items.

\paragraph{Prompt order.} Each domain's pool is read in a fixed random order per seed.
Student responses are drawn with a seed derived from the run seed and the round number,
which gives common random numbers across runs with the same seed.

\paragraph{Hardware and software.} Experiments run on a shared server with six NVIDIA
L40 GPUs of 48\,GB each, two AMD EPYC 7763 processors and 1\,TB of memory, without a job
scheduler. Jobs wait for an idle GPU and use at most two at a time, one per run. Within
a run, vLLM \autocite{kwon_vllm_2023} generates the student's responses with the current
LoRA adapter, which is reloaded after every update, and PyTorch with the PEFT library
computes the update. Scoring runs in parallel worker processes. The motivating
experiment of Section~\ref{pre:sec:motivating} ran on the School of Computing's Slurm
cluster, on NVIDIA A100 and H100 GPUs.

\section{Verification of the Testbed}
\label{imp:sec:verification}

\begin{description}[itemsep=3pt,topsep=4pt]
  \item[Answer checkers.] The checkers were validated against reference solutions rather
    than hand-labelled examples. Math-Verify accepted all 300 reference solutions in a
    sample of MATH problems. In the code domain, only problems whose reference solution
    passes in the sandbox are used (92.5\% of sampled candidates).
  \item[Sandbox.] Test programs confirmed that writes outside the working directory fail,
    network access fails, and infinite loops are stopped by the time limits.
  \item[Harness rules.] Each rule of Section~\ref{imp:sec:sandbox} was introduced in
    response to a measured failure and applies to every model. Removing appended
    self-tests recovered 286 of the base student's screening responses whose own failing
    test had caused them to be scored as missing answers. Exposing the solution's names
    to test files that omit their import raised the pass rate of KodCode reference
    solutions from about 80\% to 92.5\%.
  \item[Training loop.] Short end-to-end runs confirmed checkpointing, resumption from a
    checkpoint and the provider-free baseline, and the loop then ran the 30 main runs
    and 216 branches of the preliminary study.
  \item[Selector in simulation.] The selector of Section~\ref{imp:sec:efficiency} was run
    in a simulator calibrated to the preliminary study, with progress on Countdown and
    almost none on MATH and code. Over 200 simulated runs of 1,500 rounds it placed 56\%
    of its rounds on Countdown, against 33\% under uniform allocation. Final utility was
    nearly equal, 0.561 against 0.556, because in the simulator every arm eventually
    saturates at the same level. The simulator checks the selector's logic and is not
    evidence for any hypothesis; it also shows why curricula must be compared along the
    learning curve and not only at its end.
\end{description}

\section{Limitations of the Design}
\label{imp:sec:limitations}

\begin{description}[itemsep=3pt,topsep=4pt]
  \item[Untested objective.] The objective of Equation~\ref{imp:eq:total} has not been
    run. Whether the provider term stabilises training, and whether it produces progress
    on MATH and code, are open.
  \item[One model family.] The three providers and the student are from the Qwen2.5
    family, which white-box supervision requires here. The providers may be too alike
    for the choice between them to matter.
  \item[Ground truth in training.] The reward term needs prompts with checkable answers.
    The framework does not apply as it stands to tasks without them.
  \item[Selection-set feedback.] The selector's feedback is the change in accuracy on
    500 labelled prompts per domain, which costs an evaluation per block and is noisy
    when gains are small.
  \item[Agreement in the code domain.] Canonical answers for code are the function's
    outputs on the test inputs. For KodCode, outputs are recorded up to the first failing
    assertion in each test function, so the expected outputs influence which calls are
    recorded, although not the values compared.
  \item[Scale.] There is one student of 1.5B parameters, three domains and three seeds
    per condition, chosen to fit the available compute.
  \item[Task type.] Tasks are single-turn and verifiable, which keeps rewards cheap but
    leaves agentic and open-ended tasks untested.
\end{description}
